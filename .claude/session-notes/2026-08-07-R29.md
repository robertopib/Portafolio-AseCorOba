### Scope was measured before emitting, and the standard's estimate was wrong

§2 calls this "~20 lines". It isn't:
- The handler is **inline** in the `endpoints` array (`payload.config.ts:41-62`), not an exported
  function, so importing it means importing the whole config — DB adapter, plugins, collections.
- The `tests` CI job installs **root dependencies only** (established by R13b), so any test whose
  import graph reaches `payload` **passes locally and fails in CI**.

What kept it cheap, both verified before emitting: the handler's only Payload coupling is reading
`req.user`, so a structural param type removes the dependency; and `pingDeployHook` is already
pure (global `fetch` + one env var, no Payload import).

**One measured limit, written into the test file rather than hidden:** removing
`pingDeployHook`'s try/catch is *not* caught — the handler's own catch produces a byte-identical
body and only the status differs, and this file asserts no status there. Declaring a gap in the
file where the next reader will see it is the right habit.

### Two judgement calls worth keeping

1. **Three seam guards beyond the four branches.** A handler tested in isolation proves nothing
   about whether the config still uses it — and that risk is *created* by the extraction. Source-
   text tests now pin the wiring, the path, and the absence of a `payload` import. **Adopt this
   whenever a task extracts code for testability.**
2. **One deliberate, declared departure from "assert on the body, never the status":** a status
   assertion on the **403 only**, reason in a comment. 403 is outside R19's open question, a
   silent downgrade to 200 there is an **auth hole** rather than a redesign, and
   `PublishButton.tsx:41` branches on it. Everything else is body-only, so R19 can still change
   the status without touching a single assertion. The rule existed to stop a test that passes in
   both the broken and fixed worlds; this doesn't do that.

### ⚠️ R19's premise is factually wrong — third instance of the same failure mode

**"The editor sees success; nothing rebuilds" is false**, and has been since R11 wrote it.
`PublishButton.tsx:35-37` branches on `data.reason === 'no-hook'` and raises a red toast — *"No
hay un hook de despliegue configurado."* — since `fcf0335`, the **only** commit that file has
ever had. Conductor-verified in source at ingest.

It propagated to three places: `docs/testing-standards.md:73` (the origin), R19's roadmap detail,
and R29's roadmap detail — and I re-asserted it in R29's own task prompt without opening the
file. Nobody checked until a worker did.

**Prior instances:**
- **R17** — I claimed `studioLabel`/`roleLabel` were dead branches, from a single narrow grep.
- **R13a** — I required both twins to exit non-zero without checking `vercel.json`; shipping it
  literally would have aborted every production deploy.

**The pattern:** a claim enters an early document, later documents cite the document rather than
the code, and the prompt repeats it with the authority of the roadmap. **Rule: a factual claim
about behaviour gets re-verified in source at the moment it is put into a prompt, not inherited.**
Cheap — each of these took one grep.

### What R19's real gap is (re-scoped, not resolved)

1. **Non-UI consumers** — `curl`, monitoring, future integrations reading 200 as success. Not the
   editor.
2. **The whole signal is the `reason` string.** Until R29 nothing pinned it, so tidying it out of
   the payload would have silently killed the UI branch and degraded the specific toast to the
   generic *"No se pudo publicar"*. Now pinned by an exact `toEqual`.
3. **The 500 path is unreachable and body-identical** — the handler's `catch` fires only if
   `pingDeployHook` throws, which it is documented never to do, and the body would be identical
   anyway. **The status carries zero information the body does not.**

So R19 is a **UI/API-contract** question, not a status-code bug, and the strongest case is now
*keep 200*. R29 already delivered the unit test R19 used to bundle. Roadmap re-scoped accordingly.
