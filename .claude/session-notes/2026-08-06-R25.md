## Decisions
- **Used `PATCH .../protection/required_status_checks`, not `PUT .../protection`.** The
  sub-resource payload does not carry `enforce_admins`, `allow_force_pushes` or
  `allow_deletions`, so those fields cannot be clobbered by omission — the `PUT` form
  requires resending the entire protection object and re-creates R2's failure mode. Read
  back both branches after the edit and again after all probes; all guard fields identical.
- **Sent the `checks` array with `app_id: 15368` rather than bare `contexts`.** Pins each
  context to GitHub Actions, so a third-party app cannot satisfy a required check by
  reporting a same-named status. Matches how the existing 4 were already bound.
- **Job names copied from a live run** (`check-runs` on `a74b24d`), never retyped from the
  workflow file. Confirmed present on that run: `Site typecheck (tsc --noEmit)`,
  `Tests (vitest, offline)`, both app_id 15368.
- **Single-job re-run is the right enforcement probe here.** The timing-based alternative
  (catch the new checks pending while the old 4 are green) can never fire: `pixel-parity`
  is ~3m and the two new jobs are 22–45s, so the new checks always finish first. Re-running
  one job manufactures the needed state without touching protection or the workflow.
