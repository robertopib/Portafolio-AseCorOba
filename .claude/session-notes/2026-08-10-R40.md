## R40 — Do `governance/.claude/rules/` templates actually load here? — 2026-08-10

**Permanent.** The item's answer belongs in `docs/delivery/governance-deltas.md` §6.1 and the
roadmap. What belongs *here* is the **method**: two ways this project's "is X loaded?" checks
can return a confident wrong answer, both discovered by running the check two different ways
and getting two different results.

### Context

R34's worker reported the four upstream placeholder files under `governance/.claude/rules/`
were being loaded into every session here. The conductor checked, found the opposite, and made
it a task rather than a decision. **Both reports were accurate.** They used different tools.

### The answer, briefly

They load — **on demand, on the first Read of any file under `governance/`**, not at session
start. Every task prompt here opens with *"Read `governance/CLAUDE.md` first"*, so in practice
that is every worker session. Fixed by `claudeMdExcludes`. Claude Code `2.1.220`.
Full write-up: `docs/delivery/governance-deltas.md` §6.1. Follow-up: **R41**.

### Finding 1 — `/context` is blind to on-demand loading

The task prompt named `/context` as *the* documented check, and it is the natural one: it prints
a **Memory Files** table of what loaded. Run cold, it listed two entries. Run again after a
session had read `governance/CLAUDE.md` — with all four rule files demonstrably in that
session's context — it printed **the same two entries, byte-identical.**

`/context` tabulates **session-start** memory files. On-demand injections arrive later, as
system-reminders, and never reach that table. Following the prompt's own recommended method
would have closed R40 as a non-issue on a false negative, and the wrong answer would have been
recorded as *verified* — the strongest possible form of an inherited-claim error.

**Rule: `/context` answers "what loaded at launch", never "what is in context now".**

### Finding 2 — only the Read tool triggers instruction injection

`cat`, `sed` and `git show` read the same bytes and fire **nothing**. This is the entire
explanation for the disagreement: the conductor read `governance/` files with `git show`, and
this session's own first pass used `sed` — neither injected anything. Switching to the Read
tool injected all four immediately.

Observed live before it was tested deliberately: three of the four files were opened with the
Read tool, and the harness injected **the fourth**, unprompted, as a system-reminder.

**Rule: any "is X loaded?" check must use the Read tool. A Bash-based read measures nothing —
and measures it silently, looking exactly like a negative result.**

### Method that did work

Fresh headless sessions, one variable each: `claude -p "<read something, then report what was
auto-injected>" --allowedTools "Read"`. Five of them (cold / shallow governance read / deep
governance read / non-governance read / with the exclusion). The controls carried the weight —
the cold session and the non-governance read are what make the two positives mean something.

The exclusion was first proved with `--settings '{...}'` inline, which changes no file, and
only then written to disk and **re-proved from the real files**. Worth repeating: it makes the
"does this fix work" question answerable before committing to the fix.

The R7 shadowing question got the same treatment — a throwaway `/tmp` fixture with a project
`.claude/rules/` *and* a submodule one, each holding a unique sentinel string. **Both loaded.**
That question had a clean, cheap experiment available and would otherwise have shipped as
plausible reasoning. It is the kind of claim this project keeps getting wrong by not testing.

### Why this is the same failure mode as R31

R31 was closed because nobody had run `grep -c 'console\.'` on three files before restating a
claim about them. R40 is the mirror image: the claim was **true**, and the counter-evidence
that nearly buried it came from a check that looked rigorous and measured the wrong thing.

Inherited-claim errors are usually described as *not opening the file*. R40 adds the harder
case: **opening it with the wrong instrument.** A negative result from an instrument that
cannot detect the thing is indistinguishable from a real negative, and it is more dangerous
than no check at all, because it gets written down as verified.

### Loose ends

- The `/tmp/r40-shadow-test/` fixture was left on disk — `rm -rf` is blocked by this
  environment's Bash policy. Harmless; `/tmp` clears on reboot.
- The behaviour is **version-pinned to `2.1.220`**. `governance-deltas.md` Maintenance step 5
  now tells the next bump to re-run the test rather than trust the recorded answer.
