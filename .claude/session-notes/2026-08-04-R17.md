### The sequencing debate, resolved by measurement

R17-before-R12 had been flagged "debatable" twice on the strength of an unmeasured phrase —

That inverted the argument: R17 wasn't a pile to avoid dragging into R12, it was small — and
R12 was *blocked* on it, because the root `package.json` declared no `typescript`, no
`@types/*`, **and did not declare `react`/`react-dom` as dependencies at all** (both resolved

**Worker's re-measurement corrected the conductor's:** **29 errors in 2 files, not 33 in 3.**

the `Cannot find namespace 'JSX'` error was **an artifact of probing with `@types/react@19`**,
which dropped the global JSX namespace — under React 18 types it does not occur. Lesson: a
probe run with the wrong-major types reports errors that don't exist in the real config.

### ⚠️ Conductor error: the `studioLabel`/`roleLabel` "dead branch" claim was wrong

I wrote in the roadmap that these were "**a live defect** — the renderer reads fields that
exist in neither the type nor the content, so those branches are permanently dead, failing
silently." That was **wrong**, and the worker overturned it with evidence. Re-verified at
ingest:

- The CMS **defines both fields** — `cms/src/collections/Categories.ts:108` (`studioLabel`),
  `:119` (`roleLabel`), both localized, both with editor descriptions.
- Both exporters emit them via `putLabel`.
- The shared fallbacks live in **`content/ui.json`**, not `categories.json`:
  `es.home.studioLabel` = "Branding corporativo de:", `es.home.roleLabel` = "Mi rol", plus the
  `en` pair.
- `fieldVisible` **defaults to true when `<name>Visible` is absent**
  (`src/app/blocks/contentMeta.ts:22-25` — `return v !== false`), so the branch **renders the
  fallback**. Those strings are on the live site now.
- `content/pages.json` was last written 2026-07-14; the feature landed 2026-07-29. **The
  fixture is stale, not authoritative.**

Root cause of my error: I ran `grep studioLabel content/categories.json` → 0 and concluded
"absent from the content". Too narrow a grep, and a wrong inference from it.

**Generalisable lesson: absence from one fixture is not absence from the render path.** This
codebase's `fieldVisible` + `ui.json`-fallback pattern means a field can be fully live while
appearing nowhere in the obvious content file. Any future claim of "this field is unused"
must check the CMS collection, both exporters, `ui.json`, *and* the default-visible semantics
before asserting it.

Resolution: fields are **intended** → added to `IntroContent`. Type-only; render cannot move.

### The ratchet list — deliberately-off options with named owners

Do not enable these casually; each has a reason recorded in `tsconfig.json`:
- `noUnusedLocals` / `noUnusedParameters` — a linter's job; ESLint is broken repo-wide (**R9**).
  Enabling them would smuggle a lint gate in through the type gate.
- **`noUncheckedIndexedAccess` — the named ratchet.** Flags every `content.x[language]` read
  (e.g. `HeroSection.tsx:50`). Real risk, but the fix is runtime guards + an error boundary =
  **R18** work that changes behaviour. **Turn on once R18 lands. Never silence with `!`.**
- `@types/node` not installed, so `vite.config.ts` is outside `include` — typing its
  `__dirname` would also change `setTimeout`'s return type across all 83 site files.

### Gotchas that will bite again

1. **A prose comment in `src/` can move the stylesheet.** Tailwind v4's
   `@source '../**/*.{js,ts,jsx,tsx}'` extracts candidates from comment *text* — the word
   "static" in a new comment emitted a stray `.static{position:static}` rule and changed the
   CSS bundle. Caught and reworded. If `pixel-parity` reddens on a comment-only change, this
   is why. → belongs in `docs/testing-standards.md` §8 gotchas.
2. **`pnpm.overrides` on `@types/react` is load-bearing.** Without it an incremental install
   can leave a stray `@types/react@19` in pnpm's hoisted peer dir, producing ~**200 phantom
   TS2786 errors** from duplicate `ReactNode`. Measured, not theoretical. Clean installs were
   always fine, so CI was never at risk — this protects developers.
3. **Root TS 7.0.2 vs `cms` TS 6.0.3** — two majors in one repo (**R26**). Fine today
   (separate lockfiles/configs/jobs) but R12 may want one runner across both.
