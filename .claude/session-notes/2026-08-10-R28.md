## R28 — The fidelity gate can lose its report when output is piped — 2026-08-10

**Permanent.** Records a conductor error of a *new* kind — a verification performed under
conditions that did not resemble the target — plus the platform non-determinism that only CI
exposed.

### Context

R13a's value is the **message**, not the exit code: when the two content emitters diverge, the
gate prints which file and which JSON path disagree. R13b found that message could vanish.
`console.error(...)` immediately before `process.exit(...)` loses buffered output, because
`process.exit` does not drain queued stream writes.

### ⚠️ Conductor error: I verified the right claim under the wrong conditions

I told the worker *"both candidate fixes verified at 200 KB"*, having measured `fs.writeSync`
delivering all 200,001 bytes. **That passed only because my scratch script imported nothing
else.**

A bare `fs.writeSync` delivers in full only while fd 2 is still **blocking**. libuv flips it to
`O_NONBLOCK` the moment Node instantiates `process.stderr` — after which a bare `writeSync`
truncates at 65,536, *identical to the bug it was meant to fix*. Re-confirmed at ingest: adding
one `import { execPath } from 'node:process'` to my own repro dropped it **200,001 → 65,536**.
An import is enough; no console call required. **Every real script is already in the truncating
state.**

So the offset loop and EAGAIN retry are the actual fix, not defensive garnish — and the worker
replaced a busy-wait with `Atomics.wait` (1.01 s → 0.08 s user CPU against a reader stalled 1 s).

**This is a new failure mode, distinct from the previous three.** `studioLabel` (R17), the
exit-code criterion (R13a) and R19's premise (R29) were all claims inherited from a document
without opening the code. Here I *did* measure — but in a setup that shared almost nothing with
the target.

> **Rule: a verification is worth only what its setup shares with the real thing.** A scratch
> script is not a 1,000-line script with imports. When the measurement is about process/stream
> behaviour, the imports *are* the environment.

**My platform generalisation was wrong too.** I reported a clean 65,536 truncation "every time" —
macOS-specific. On **Linux / Node 24 the bug is non-deterministic**: five runs gave
`200000, 146176, 146176, 146176, 146176`, i.e. sometimes no loss at all. The fix delivered
200,000 5/5 on both.

### A fourth site I failed to list

The prompt named three. The **`FIDELITY_GATE=0` warning branch** prints the same full report and
falls through to the trailing `exit(0)` — truncating identically, at exit code 0 (65,528 →
240,980). I had listed the sites that exit *non-zero* and missed the one that warns then exits
zero. **The bug is `console.*` before ANY `process.exit`, not before a failing one.** That
framing is what R31 needs.

### Why `fs.writeSync` and not `process.exitCode`

`export-content.ts` ends in an unconditional `process.exit(0)` that is **load-bearing** — Payload
holds an open pg pool, so the process would not exit on its own — and it would silently override
an assigned `exitCode`. Proving otherwise needs a DB run the task forbade. Writing synchronously
touches no exit-control flow at all. Applied to *all* output in both scripts rather than only the
exit-adjacent lines, because mixing `writeSync` with buffered `console` reorders output.

### The zero-byte case — reproduced, and it is this bug one step worse

What survives is one pipe buffer **in total**, shared with everything printed earlier. If prior
output already filled it, the report's first `write()` gets EAGAIN, the whole message is queued,
and `process.exit` drops all of it.

| Prior output (macOS/Node 22) | Report delivered, unfixed |
|---|---|
| none | 65,536 of 200,000 |
| 8 KiB | 57,344 (= 65,536 − 8,192) |
| 64 KiB, stalled reader | **0**, 5/5 runs |
| 64 KiB, prompt reader | **0** in 9/20, 65,536 in 11/20 |

Two independent sources of the intermittency R13b saw — buffer sharing, and platform
non-determinism.

### Test-design notes worth keeping

- The **vacuity guard samples 10 runs** and asserts at least one lost bytes, rather than asserting
  a single run truncates. The strict single-run form was written first per the agreed rule, went
  red on CI (because of the Linux non-determinism above), and was downgraded rather than shipped
  flaky. Correct trade: the guard still fails if the bug disappears entirely.
- The primary fixed-path test **repeats 5×**, since "deterministic where the bug is not" is half
  the claim.
- One mutation found a real gap: reverting `main({ log = syncConsole })` to `log = console`
  **passed**, because the call site is `log.error`. The invariant was widened from "no `console.*`
  calls" to "no `console` token in any code line".
