## R40 — conductor's note: how the disagreement was resolved — 2026-08-10

**Permanent.** The worker's own note (`2026-08-10-R40.md`) records the experiment and the two
methodological rules. This one records the conductor side: a challenge that was wrong, why it
was wrong in two independent ways, and why raising it was still the right move.

### What happened

R34's worker reported that `governance/.claude/rules/`'s four placeholder templates auto-load
into every session here. The conductor challenged it before emitting R40, citing the Claude
Code docs (`.claude/rules/` is a *project-level* path; discovery walks *up* the tree) and a
direct observation: *"this session has read many files under `governance/` and that content has
never appeared as loaded instructions."*

**The worker was right. The premise is true**, established by five controlled headless
sessions: cold → no; Read `governance/CLAUDE.md` → all four injected; Read a *deep* governance
file → all four; Read a non-governance file → none; with `claudeMdExcludes` → none.

### Why the conductor's evidence was wrong — two independent reasons

1. **Only the `Read` tool triggers injection.** `cat`, `sed` and `git show` read the same bytes
   and fire nothing. Every governance file the conductor examined after the bump went through
   `sed` or `git show`.
2. **Found at ingest, and the worker could not have known it:** the conductor *did* use the
   Read tool on `governance/CLAUDE.md` — once, during the T1–T6 planning session, **before R33
   bumped the submodule.** At the `e85041e` pin there is no `.claude/` directory at all
   (`git -C governance ls-tree e85041e .claude/` → empty). Injection was impossible.

So the observation was accurate and doubly inapplicable: wrong tool, and before the files
existed.

### The rule this produces

**"I looked and saw nothing" is only evidence if you can state what would have made it
visible.** Neither condition — which tool triggers the load, or whether the files existed at
the time — was checked before the observation was offered as a counter-argument. A negative
observation needs its own positive control, exactly as the worker's session D (read a
non-governance file → nothing) and session E (exclusion applied → nothing) provided.

This is the **sixth** error in this project's sequence, and the third distinct *kind*:
- **Four were citing a document instead of the code** — `studioLabel` (R17), the exit-code
  criterion (R13a), R19's premise (R29), the 400-line/permanent-notes claims (R34).
- **One was citing a model instead of the mechanism** — i.i.d. Bernoulli applied to a
  scheduling race (R37).
- **This one is offering a null result without establishing its sensitivity.**

### Why raising it was still right

The challenge was wrong and it was *productive*: it converted "a worker mentioned observing
this" into a controlled experiment with negative and treatment controls, a pinned Claude Code
version, and a documented fix. R31 was closed on exactly this kind of challenge and was a real
non-issue. The cost of asking is one verification task; the cost of not asking is a Medium item
worked on an unexamined premise.

**What should change is not "challenge less" but "state the falsifier".** Had the challenge
read *"I saw nothing — but I only used `git show`, and I have not checked whether that
triggers discovery"*, the disagreement would have been correctly framed from the start.

### The near-miss worth remembering

The R40 prompt prescribed **`/context`** as the verification method. It returns a **false
negative** here: after a governance read, with all four files demonstrably in context, its
**Memory Files** table is byte-identical to a cold session's — it tabulates session-start
memory only. **A worker following the prompt literally would have closed R40 as a non-issue and
recorded the wrong answer as verified.** The worker went past the prescribed method on its own
initiative, which is the only reason the answer is right.

Conductor rule: when prescribing a verification method, say what it is *known* to cover. A
method named in a prompt carries the authority of the prompt.
